# Ship one image, install it through RouterOS Apps

As of November 2026, tikontrol should be built as four static musl binaries on one x86 GitHub runner with cargo-zigbuild. Each binary is copied into a `FROM scratch` image that runs as UID 65532 and is published to ghcr.io as a plain multi-arch index, with **no BuildKit attestations in the index** and gzip layers. On the router, the main install path is a **third-party app store**: one YAML file on GitHub Pages that the user adds once with `/app/settings set app-store-urls=...`. tikontrol then shows up in WinBox and WebFig Apps next to MikroTik's own apps and installs with one click. This path needs RouterOS 7.22 or later (7.25+ is recommended) and arm64 or x86 hardware. Two things cannot be automated. The `container` device-mode needs a physical button press or a cold reboot, and the router side of least privilege (a custom group, the user, the api-ssl certificate and the service address list) is a set of router writes. A small, idempotent `.rsc` script shows those writes and the user runs it. Upgrades are tag bumps in the store YAML that the user applies with **Update**, never silently. Verification has to happen off the router: RouterOS cannot check a signature, so GitHub artifact attestations, checksums and immutable releases protect the people who verify, and TLS to ghcr.io plus pinned version tags is the only protection on the router itself. One caveat applies to everything below about RouterOS. The research sessions could not reach help.mikrotik.com, manual.mikrotik.com, forum.mikrotik.com or download.mikrotik.com, so those facts rest on search snippets, GitHub mirrors of the changelog and live-CHR data republished by third parties. That is why the design ends with a test list rather than a claim that it works.

## The RouterOS evidence is second-hand, so the design is built around testing

The build and signing facts are first-hand. They come from upstream repositories, from `git ls-remote` and from builds the project ran locally. The RouterOS facts are not. MikroTik's own manual and changelog pages were blocked in every research session. Their content was reconstructed from search-engine snippets, from changelog text reproduced in the release notes of `elseif/MikroTikPatch` (a patched-RouterOS project whose binaries must not be trusted, though its notes quote MikroTik's text) ([MikroTikPatch releases](https://github.com/elseif/MikroTikPatch/releases)), and from **tikoci/restraml**, which dumps `GET /rest/app` from a live CHR of each RouterOS version ([restraml 7.25 app.json](https://raw.githubusercontent.com/tikoci/restraml/main/docs/7.25/app.json)). The restraml dump is the strongest RouterOS source available, because it is RouterOS's own output for its 102 built-in apps. Community guides fill the remaining gaps, and they disagree in places. Examples are whether `healthcheck` works in app YAML (it does on 7.25, but a 7.22-era guide says it does not), whether the update command is `/app/update` or `/app/upgrade`, and whether `network-outgoing-access` arrived in 7.23 or 7.24 ([GustavoGustik KB](https://github.com/GustavoGustik/mikrotik-custom-apps-knowledgebase); [restraml PR #117](https://github.com/tikoci/restraml/pull/117); [Orb docs PR #134](https://github.com/orbforge/orb-docs/pull/134)). In each conflict, this report prefers the most recent source that was checked on hardware. Every property name in an installer must still be confirmed with `?` completion on CHR before it ships.

## One x86 runner cross-builds all four binaries, and only armv5te needs care

The coordinator checked the toolchain locally, and those results override the research notes. **cargo-zigbuild 0.24 with zig 0.17 built release binaries for `armv7-unknown-linux-musleabihf` (2.4 MB), `aarch64-unknown-linux-musl` (2.5 MB) and `x86_64-unknown-linux-musl` (3.0 MB)**. rustup also ships a prebuilt std for `armv5te-unknown-linux-musleabi`. That contradicts the notes, which read the platform-support table as listing armv5te under Tier 3 ([rust-lang platform-support.md](https://github.com/rust-lang/rust/blob/master/src/doc/rustc/src/platform-support.md)). The local check wins, so `-Zbuild-std` and nightly are not needed. The only armv5te build failure was the project's own use of `std::sync::atomic::AtomicU64`. That is expected, because the target spec sets `max_atomic_width: Some(32)` ([rustc target spec](https://doc.rust-lang.org/stable/nightly-rustc/src/rustc_target/spec/targets/armv5te_unknown_linux_musleabi.rs.html)). The fix is to use 32-bit counters or a `Mutex<u64>`. After that, the armv5te job must stay in every PR build, because any new dependency that uses 64-bit atomics breaks only that target. The real remaining risk is **ring**. Its CI tests armv6 gnueabi, armv7 and aarch64 musl but **not armv5te** ([ring ci.yml](https://github.com/briansmith/ring/blob/main/.github/workflows/ci.yml)), so a TLS handshake on a real ARMv5 CPU is unproven. The zigbuild README also warns that zig can miss `compiler_rt` symbols and does not pass CPU features to clang ([cargo-zigbuild README](https://github.com/rust-cross/cargo-zigbuild/blob/main/README.md)). `cross` has an `armv5te-unknown-linux-musleabi` image with QEMU test support and is the fallback if zig breaks ([cross README](https://github.com/cross-rs/cross/blob/main/README.md)). Its last release is still v0.2.5, though, which is why ripgrep pins it ([ripgrep release.yml](https://github.com/BurntSushi/ripgrep/blob/master/.github/workflows/release.yml)).

The CI split follows from this. PR CI runs lint (fmt, clippy, `npm run check`, `node --test tests/hardware.test.ts`, the UI build), `cargo deny check` and `npm audit`, then native tests on `ubuntu-24.04` and on the free `ubuntu-24.04-arm` runners, which have been GA for public repos since August 2025 ([GitHub changelog](https://github.blog/changelog/2025-08-07-arm64-hosted-runners-for-public-repositories-are-now-generally-available/)). The two 32-bit ARM targets get a build-only zigbuild job, plus a QEMU-user smoke run on main. That smoke run should pin an ARMv5 CPU model so that an ARMv7 instruction in the v5 binary fails in CI and not on a hEX Refresh. The UI is built once and passed as an artifact. Supply-chain hygiene is the current standard. Every action is pinned to a full SHA with a version comment (the notes list verified SHAs, for example `actions/checkout@3d3c42e…` for v7.0.1). Workflows start from `permissions: {}`, checkout uses `persist-credentials: false`, zizmor and actionlint lint the workflows, and Dependabot runs with a 7-day cooldown ([zizmor audits](https://github.com/zizmorcore/zizmor/blob/main/docs/audits.md)). The repository should turn on GitHub's "require SHA pinning" policy ([GitHub changelog](https://github.blog/changelog/2025-08-15-github-actions-policy-now-supports-blocking-and-sha-pinning-actions/)). The release workflow restores no caches and disables setup-node's automatic npm cache, which closes the cache-poisoning path ([setup-node README](https://github.com/actions/setup-node/blob/main/README.md)).

Release automation should stay plain, in line with the "few dependencies" rule. A protected `v*` tag triggers the workflow. The workflow checks that the tag matches the versions in `Cargo.toml` and `package.json`, creates a draft release with `gh`, uploads assets, attests them, then publishes. **Immutable releases** (GA October 2025) lock the tag and add a release attestation. Assets must be attached before publishing, though, because manual uploads afterwards reportedly break that attestation ([GitHub changelog](https://github.blog/changelog/2025-10-28-immutable-releases-are-now-generally-available/); [community #178351](https://github.com/orgs/community/discussions/178351)). release-please v5 is worth adding later if keeping the changelog by hand becomes tedious. dist does not cover the custom scratch image ([cargo-dist README](https://github.com/axodotdev/cargo-dist/blob/main/README.md)).

## The image has three or four platforms, no attestation entries, and arm32 built as v5

The Dockerfile contains no `RUN`, so nothing needs emulation. It is `FROM scratch`, then `COPY --chmod=0755 dist/${TARGETARCH}${TARGETVARIANT}/tikontrol /tikontrol`, then `USER 65532:65532`, then `ENTRYPOINT ["/tikontrol"]`. Docker's own guidance is to cross-compile outside the emulator and select files by `TARGETARCH`/`TARGETVARIANT` ([docker multi-platform docs](https://github.com/docker/docs/blob/main/content/manuals/build/building/multi-platform.md)). The image binaries are then byte-identical to the release assets, so one checksum file covers both. Two flags matter on RouterOS. First, BuildKit adds provenance attestations to the index by default, and on GHCR these appear as `unknown/unknown` platform entries ([docker attestation docs](https://github.com/docker/docs/blob/main/content/manuals/build/metadata/attestations/_index.md); [GitHub community #45969](https://github.com/orgs/community/discussions/45969)). Non-Docker runtimes have tripped over them ([drone-buildx PR 137](https://github.com/drone-plugins/drone-buildx/pull/137)), and no source says how RouterOS's simple matcher handles them. So set `provenance: false` and `sbom: false`, and attach provenance with `actions/attest` and `push-to-registry: true` instead. That stores it as a referrer outside the index ([actions/attest README](https://github.com/actions/attest/blob/main/README.md)). Second, zstd layer extraction only arrived in the 7.22 cycle ([newreleases 7.22rc2 mirror](https://newreleases.io/project/github/elseif/MikroTikPatch/release/7.22rc2-arm64)), so use **gzip layers** and older routers keep working. With one 2–3 MB layer per platform, the image also leaves little room for the "failed to extract layer" bugs seen with large images ([forum 263061](https://forum.mikrotik.com/t/solved-cant-import-armv5-image-from-dockerhub-failed-to-extract-layer-routeros-container-hex-s-e60iugs-en7562ct-cpu/263061)).

32-bit ARM is the subtle part. RouterOS reports `arch="arm"` for both ARMv7 and EN7562CT boards. A hEX Refresh pulling a multi-arch image received the ARMv7 entry and died with "signal 4 (Illegal instruction)" ([netbird #3847](https://github.com/netbirdio/netbird/issues/3847)). MikroTik's docs say EN7562CT runs only arm32v5 images ([Container docs, snippet](https://help.mikrotik.com/docs/spaces/ROS/pages/84901929/Container); [tor-mikrotik README](https://github.com/n4tash4/tor-mikrotik)). It is unknown whether RouterOS honours the OCI `variant` field. The safe default is therefore one 32-bit entry, **`linux/arm/v5`, built from the armv5te binary**, which runs on every 32-bit MikroTik. That is the same call jmrplens/mikroscope made when it set GOARM 5 as its default ([mikroscope PR 7](https://github.com/jmrplens/mikroscope/pull/7)). Add an `arm/v7` entry only if tests on a real ARMv7 board and on an EN7562CT board show that RouterOS picks the right variant. For a web app whose heavy lifting is a few TLS sessions to the router, the speed lost on v5 is unlikely to matter. Per-platform `docker save` tars (`type=docker`, one platform each) ship as release assets for offline `/container/add file=` installs. No source shows RouterOS choosing a platform from a multi-arch tar ([Container docs, snippet](https://manual.mikrotik.com/docs/containers/)).

Pin by **version tag** (`ghcr.io/example-owner/tikontrol:0.4.0`), not `latest`. No source confirms that digest references work in `remote-image` or the app `image:` field, so they must be tested before they are used. The package must be public. Otherwise every router would hold a GHCR token in `/container/config password=`, which breaks the secrets rule ([GitHub Docs: Container registry](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry)).

## The app store is the one-click path, and plain containers are the fallback for arm32

Since 7.22, RouterOS has had custom apps and a configurable `app-store-urls` setting that points at a YAML **array** of app definitions ([Apps manual, snippet](https://help.mikrotik.com/docs/spaces/ROS/pages/343244823/Apps); [GustavoGustik KB](https://github.com/GustavoGustik/mikrotik-custom-apps-knowledgebase)). Store apps appear in the WinBox/WebFig Apps catalog. Orb, a commercial vendor, ships its MikroTik sensor exactly this way. On 7.24.5 its catalog loaded about 10 seconds after the URL was set, or after **Apps > Settings > Apply** ([Orb docs PR #134](https://github.com/orbforge/orb-docs/pull/134)). kernelorg serves a store straight from `raw.githubusercontent.com`. It generates `apps.yaml` from per-app files at release time and checks that every image tag and arch exists in the registry ([kernelorg/mikrotik-apps](https://github.com/kernelorg/mikrotik-apps)). tikontrol should copy that pattern. The release workflow renders `tikontrol.tikappstore.yaml` with the new tag, validates it against tikoci's [store schema](https://tikoci.github.io/restraml/routeros-app-yaml-store-schema.latest.json), and publishes it to GitHub Pages. GitHub Pages is reported to parse correctly and does not redirect ([KB app-store doc](https://github.com/GustavoGustik/mikrotik-custom-apps-knowledgebase)). A single-app `tikontrol.tikapp.yaml` is published next to it for `/app/add` and for REST `PUT /rest/app {"yaml-url": …}` ([tikoci routeros-app-yaml skill](https://github.com/tikoci/routeros-skills/blob/main/routeros-app-yaml/SKILL.md)).

The YAML schema, taken from RouterOS's own re-emitted built-ins, fixes most of the content. **There is no memory, network-mode or HTTPS key**, only fields such as `name`, `descr`, `category`, `supported-archs` (7.25), `secrets`, `services` and `volumes` ([restraml schema](https://raw.githubusercontent.com/tikoci/restraml/main/docs/routeros-app-yaml-schema.latest.json)). A sketch with fictional values:

```yaml
- name: tikontrol
  descr: Simple web UI for this router
  page: https://github.com/example-owner/tikontrol
  category: networking
  supported-archs: [arm64, x86]
  default-credentials: "setup:[secret:setup_token]"
  secrets:
    setup_token:
  services:
    web:
      image: ghcr.io/example-owner/tikontrol:0.4.0
      user: "65532:65532"
      ports:
        - "8443:8443:web-https:tcp"
      environment:
        TIKONTROL_ROUTER: "[routerIP]:8729"
      secrets: [setup_token]
      volumes:
        - data:/data
      healthcheck:
        test: [CMD, /tikontrol, healthcheck]
        interval: 30s
        retries: "3"
      restart: unless-stopped
  volumes:
    data:
```

Each choice here has a reason. The `secrets:` block makes RouterOS generate a random value (7.24+), hide it from exports, and mount it at `/run/secrets/setup_token` ([7.24 notes](https://github.com/elseif/MikroTikPatch/releases/tag/7.24); [restraml 7.25 app.json](https://raw.githubusercontent.com/tikoci/restraml/main/docs/7.25/app.json)). tikontrol's first-run page can then require that token, and the user reads it from the app's `default-credentials` in WinBox. No setup secret ever travels through a URL or the browser's storage. The healthcheck uses a binary subcommand because a scratch image has no `wget`, and RouterOS 7.25 does run YAML healthchecks inside the container ([restraml PR #117](https://github.com/tikoci/restraml/pull/117)). All state lives in the named volume, because an app update replaces the rootfs ([Orb docs PR #134](https://github.com/orbforge/orb-docs/pull/134)). The `web-https` label appears on three built-ins, which suggests apps that serve their own TLS. Whether it stops RouterOS's default `use-https=yes` reverse proxy from forwarding plain HTTP to an HTTPS port is untested. That matters because the alternative, RouterOS-managed HTTPS, requires `/ip/cloud`, a wildcard Let's Encrypt certificate under `routingthecloud.com` named after the router serial, and moving `www-ssl` off 443 ([KB networking](https://github.com/GustavoGustik/mikrotik-custom-apps-knowledgebase)). That is a cloud dependency and a router change that tikontrol should not impose by default.

The app path has three real limits. First, `supported-archs` filtering is a 7.25 feature. On 7.25, 71 of the 102 built-ins are arm64/x86 only ([restraml 7.25 app.json](https://raw.githubusercontent.com/tikoci/restraml/main/docs/7.25/app.json)), and `/app` for ARM32 is still only a 7.26beta item ([7.26beta announcement](https://forum.mikrotik.com/t/7-26beta-development-is-released/273582)). So hEX Refresh and hAP ax S owners need the plain-container path for now. The hAP ac², with 128 MB RAM and almost no free flash, should be declared unsupported as a host, as the earlier hardware research concluded ([hAP ac² product page](https://mikrotik.com/product/hap_ac2)). Second, the YAML cannot set `memory-max`. The project rule requires one, but changing app-managed containers with `/container/set` desynchronises `/app` ([KB auto-managed infra](https://github.com/GustavoGustik/mikrotik-custom-apps-knowledgebase)). Until a test shows that a per-container `memory-max` survives an app update, this is an **open gap against the container rule** and must be reported as one, not hidden. The global `/container/config memory-max` limit works, but it affects every container on the router. Third, the store URL is a supply-chain trust root. Whoever controls that YAML chooses the image and environment that run on the router. It must be published only by the tag-protected release workflow, and users who want to pin should get a per-version URL as well.

The plain-container path covers arm32 and routers without `/app`. It is a one-liner that fetches an `.rsc` over verified TLS and imports it: `/tool/fetch url="https://example-owner.github.io/tikontrol/install.rsc" check-certificate=yes dst-path=tikontrol-install.rsc; /import file-name=tikontrol-install.rsc verbose=yes`. Recent RouterOS ships a built-in root store whose documented default `builtin-trust-store` includes both `fetch` and `container`, so `check-certificate=yes` works on fresh installs. The script should still check that setting and the clock first ([Certificates manual, snippet](https://manual.mikrotik.com/docs/authentication-authorization-accounting/certificates/); [eworm-de README](https://github.com/eworm-de/routeros-scripts/blob/main/README.md)). Fetch to a file, not `output=user`, which truncates at 64,512 bytes ([fetch CLI reference](https://manual.mikrotik.com/docs/cli-reference/tool/fetch/)). Host the script on Pages rather than on release-asset URLs, which redirect, because sources disagree on whether fetch follows redirects by default ([mikrotikdocs.fyi Fetch](https://mikrotikdocs.fyi/tools/fetch/)). Property names changed between 7.20 and 7.23 (`envlists`, `mountlists`, veth `dhcp`, `cmd` effectively required, `restart-policy` and healthcheck) ([7.21 notes](https://forum.mikrotik.com/t/v7-21-stable-is-released/267773); [community.routeros changelog](https://docs.ansible.com/projects/ansible/devel/collections/community/routeros/changelog.html); [tailscale-mikrotik README](https://github.com/Fluent-networks/tailscale-mikrotik)). The script should therefore **refuse anything below 7.22**, not branch across five syntaxes. Routers on 7.18–7.21 can still be managed from a tikontrol running on a home server, which is what the 7.18 API minimum is for. The script creates a dedicated bridge and a static veth. A static address is needed so that the firewall and service rules can name it. It also creates a mountlist on an existing ext4 disk (it never formats one), a container with explicit `cmd`, `dns`, `memory-max`, `start-on-boot=yes` and `restart-policy`, and pins `remote-image` to the full `ghcr.io/...:0.4.0` reference. That avoids changing the global `registry-url` ([registry research, forum 183044](https://forum.mikrotik.com/t/cont-not-ok-registry-auth-response-403-when-adding-a-container/183044)). Every object carries `comment="tikontrol"` and is found with `[find comment="tikontrol"]`. Re-runs are therefore idempotent, and an uninstall script removes exactly what was added ([forum: idempotent script](https://forum.mikrotik.com/t/how-to-write-idempotent-script/155596)). `:onerror` wraps each step ([Scripting manual, snippet](https://help.mikrotik.com/docs/display/ROS/Scripting)).

## Device mode and least privilege stay manual, and that is correct

The `container` feature is off in every device mode. It turns on only after `/system/device-mode/update container=yes` followed by a reset-button press or cold reboot within `activation-timeout` (default 5 minutes). A soft reboot cancels the change, and three failed attempts lock out further tries for a while ([Device-mode CLI reference, snippet](https://manual.mikrotik.com/docs/cli-reference/system/device-mode/update/)). The container package also has to be present. Both installers must therefore run as **two phases**. Phase one runs the preflight: version, architecture, package, device-mode, disk and trust store. If container mode is off, it prints the exact command plus "press the reset button within 5 minutes" and stops. It never starts the mode change itself. Phase two is the same one-liner run again after the reboot. Home mode reportedly also disables `fetch` and `scheduler` ([Device-mode manual, snippet](https://help.mikrotik.com/docs/spaces/ROS/pages/93749258/Device-mode)), which would break the one-liner before it can explain anything. So the README has to give the device-mode command first, with `fetch=yes` if a home-mode test confirms it is needed.

Nothing in `/app` provisions a RouterOS user or a certificate. MikroTik's own `mikrodash` app is the cautionary example: it connects to `[routerIP]` on **plain 8728 with `ROUTER_TLS: false` and user `admin`** ([restraml 7.25 app.json](https://raw.githubusercontent.com/tikoci/restraml/main/docs/7.25/app.json)). tikontrol needs the opposite. That means a custom group with only `read` and `api` (never the built-in `read` group), a user with `address=` limited to the container subnet (172.18.0.0/24 for internal apps, or the static veth address), an api-ssl certificate, and `/ip/service set api-ssl address=` narrowed the same way. Changing `/ip/service` is high-risk under the project's own rules, because a wrong address list can lock out other API users. The internal app bridge also joins the LAN interface list, so the default firewall already accepts its traffic ([KB networking](https://github.com/GustavoGustik/mikrotik-custom-apps-knowledgebase)). A narrow input rule is better than relying on that. These writes belong in a separate `router-access.rsc`. It prints every change before applying it, tags each object for rollback, and has an `undo` companion, which keeps it within Safe apply. For credentials, the cleanest option, pending a test, is to have the script read the RouterOS-generated app secret and use it as the user's password. The password would then never leave the router, and the container would read it from `/run/secrets/`. If scripts cannot read app secrets, the user types the password once into tikontrol's first-run form, and tikontrol encrypts it at rest in the volume. For the api-ssl certificate, tikontrol should pin the fingerprint on first connect and show it for comparison with `/certificate print`, because `[routerIP]` is an IP address that no public CA will cover.

## Upgrades are store tag bumps that the user applies

On the app path, a release changes the image tag in the store YAML. The user clicks **Update**, or runs `/app/update`, the name Orb used on 7.24.5. RouterOS then pulls the new tag, replaces the rootfs and keeps the volume. RouterOS never deletes old layers on update ([Orb docs PR #134](https://github.com/orbforge/orb-docs/pull/134)). At about 3 MB per release, tikontrol is the least affected image possible, but the docs should still describe the cleanup. `auto-update` exists per app and globally, but sources disagree on whether it runs at boot or periodically ([tikoci skill](https://github.com/tikoci/routeros-skills/blob/main/routeros-app-yaml/SKILL.md); [KB](https://github.com/GustavoGustik/mikrotik-custom-apps-knowledgebase)). The YAML should leave it off. On the plain-container path, `/container/repull` (7.22+) re-pulls the image after the script has set the new `remote-image` tag ([Tangentsoft, snippet](https://tangentsoft.com/mikrotik/wiki?name=Container+Limitations)). Rollback means setting the previous tag, which the script records in the object comment, and repulling. tikontrol itself must not upgrade its own container. That would need `/container` write rights and break least privilege. Under the privacy rule it should not check GitHub for updates by default either. An opt-in "check for updates" that fetches a small `latest.json` is the most it should do.

Verification follows the same split. CI writes `SHA256SUMS` over the binaries and tars and attests them with `actions/attest` (`subject-checksums`). It also attests the image index digest with `push-to-registry: true` ([actions/attest README](https://github.com/actions/attest/blob/main/README.md)). Users who care run `sha256sum -c` and `gh attestation verify` on a PC before uploading a tar, or inspect the tag's digest before clicking Install. Cosign keyless signing would add a second story with no added benefit on the router. Cosign v3 does keep signatures out of the index as OCI 1.1 referrers, so it is safe to add later ([cosign CHANGELOG](https://github.com/sigstore/cosign/blob/main/CHANGELOG.md)). On the router, the trust chain is TLS to ghcr.io and Pages, a tag that only the protected release workflow can create, and immutable releases. The installer one-liner could also carry a pinned hash of `install.rsc` if `:convert transform=sha256` exists. Sources disagree on that, and only sha512 has been seen working on 7.16.2 ([forum: Base64 and SHA256](https://forum.mikrotik.com/t/base64-and-sha256-function-for-scripting/164889)). The docs should state the weakness honestly: RouterOS installs whatever the tag points to.

## Recommended release and install design

| Area | Decision |
|---|---|
| Build | Tag-triggered GitHub Actions, one `ubuntu-24.04` job, cargo-zigbuild for `x86_64`, `aarch64`, `armv7`, `armv5te` musl; native tests on x86 and `ubuntu-24.04-arm`; QEMU ARMv5 smoke test; `cross` (pinned) as armv5te fallback |
| Hygiene | SHA-pinned actions, `permissions: {}`, zizmor + actionlint, Dependabot 7-day cooldown, `cargo deny` + `npm audit`, no caches in release |
| Image | `FROM scratch`, `USER 65532:65532`, `ghcr.io/example-owner/tikontrol:X.Y.Z` public; platforms `linux/amd64`, `linux/arm64`, `linux/arm/v5` (add `arm/v7` only after a variant test); `provenance: false`, `sbom: false`, gzip; per-platform `docker save` tars |
| Integrity | `SHA256SUMS`, `actions/attest` for assets and image digest (pushed as referrer), immutable releases, draft → upload → publish |
| Primary install (7.22+, recommend 7.25+, arm64/x86) | README one-time steps: container package, device-mode + button, `/app setup`, then append the Pages store URL to `app-store-urls`; click Install; first-run page asks for the RouterOS-generated setup token |
| Router access | Separate `router-access.rsc`: custom `read,api` group, address-limited user, api-ssl cert, narrowed api-ssl address list, input rule; prints changes; `undo` script; tikontrol pins the cert fingerprint |
| Fallback install (7.22+, arm32 or no `/app`) | Two-phase `install.rsc` via verified `/tool/fetch`; static veth, mountlist, `memory-max`, full-host `remote-image`, `comment="tikontrol"` on everything; uninstall script |
| Upgrades | Store tag bump + user-clicked Update (app) or tag set + `repull` (container); no auto-update by default; opt-in update check only |
| Unsupported | RouterOS < 7.22 on-router (manage from a home server instead); hAP ac² as a host |

## Ordered test list for CHR and real hardware

The order front-loads the tests whose failure would change the design.

1. On a 7.25.1 CHR (x86), pull the published index from ghcr.io by `/container/add remote-image=ghcr.io/example-owner/tikontrol:X.Y.Z`. Confirm that the full-host form works without touching `registry-url`, that gzip extracts, and that the provenance-free index is accepted. Then push a test tag *with* BuildKit attestations to see whether `unknown/unknown` breaks the pull.
2. On the same CHR, try a `@sha256:` digest reference in `remote-image` and in app `image:`.
3. Check that the scratch container runs as UID 65532 and can write to an app named volume and to a `/container/mounts` directory. Volume ownership is the most likely silent failure for a non-root image.
4. Connect from inside the container to `[routerIP]:8729` with a `read,api` custom user. Confirm cert pinning, the narrowed `api-ssl address=`, and the narrow input rule. Prove that a write such as `/system/identity/set` is **rejected by the router**, as the read-only rule requires. Test with and without `network-outgoing-access=no`.
5. Add the store URL on 7.22, 7.24 and 7.25. Measure when the catalog appears, check that `supported-archs` hides the app on non-matching archs and does not break 7.22–7.24 parsing, check whether GitHub Pages' content type parses, and check that appending keeps another store's URL.
6. Install from the store. Check that `[secret:setup_token]` is mounted and shown in `default-credentials`, that the `CMD /tikontrol healthcheck` healthcheck turns healthy, and what `web-https` does with `use-https=yes` and `use-https=no`.
7. Bump the store tag and run Update. Confirm that the volume survives, that rollback to the previous tag works, that the old layers' disk use matches expectations, and whether a per-container `memory-max` set after install survives the update.
8. Check whether a RouterOS script can read the app's generated secret to create the RouterOS user, and whether `:convert transform=sha256` exists.
9. Run the plain-container `install.rsc` end to end on 7.22, 7.24 and 7.25. Check the device-mode refusal message, idempotent re-run, `repull` upgrade and rollback, `memory-max` enforcement (OOM detection), and uninstall leaving nothing tagged behind.
10. On an ARMv7 board, pull the index and confirm that the v5 binary runs with an acceptable TLS handshake time. If an `arm/v7` entry is added, confirm which variant RouterOS picks.
11. On an EN7562CT board (hEX Refresh or hAP ax S), pull the index and import the arm/v5 tar. Confirm that there is no SIGILL, that ring's TLS handshake to the router works, and how much memory it uses. Then test `/app` on 7.26beta with `supported-archs` including `arm_v5`.
12. On a home-mode device such as a hAP, confirm whether `fetch` is disabled and what the exact device-mode command must include.
13. On a hAP be³ Media (arm64, 2 GB), run the full happy path from a factory-default config on the newest stable, including `/app setup` on a USB or microSD disk.

## Conclusion

The research changes where the work sits. Building and signing a 3 MB static binary is solved, and the only real risks are ARMv5-specific: 64-bit atomics, which the project is already fixing, and ring's untested assembly fallbacks. The hard part is RouterOS. Its app store is good enough to make tikontrol look like a first-party app with one click, but it was designed for apps that trust the router's defaults. Those defaults include plain API, `admin`, cloud HTTPS and no memory limits, and tikontrol's security rules reject every one of them. The seamless experience will therefore come from tikontrol's first-run page doing the explaining, while the YAML stays minimal: it shows the token, prints the exact router-access commands, and pins the certificate. It will not come from a cleverer installer.

The security story also has a gap that no CI step can close: RouterOS cannot verify what it pulls. Until MikroTik adds signature checks for images or store YAML, tikontrol's integrity on the router rests on GitHub's tag protection and TLS. The docs should say that plainly. The memory-limit gap on the app path should be tracked as an open issue against the container rule until test 7 resolves it.
