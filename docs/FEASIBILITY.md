# Shrink tikontrol before writing any backend

Tikontrol is technically possible, but it should not be built as a general "UniFi for MikroTik". A separate home server is the best host, a container on the hAP be³ Media is a plausible second, and the hAP ac² is ruled out as a host and works only as a managed device. The hard limits sit elsewhere: RouterOS has no transactions or commit-confirm, its APIs change in nearly every minor release, and it exposes no per-client application data. MikroTik's CMR does not make the project pointless, because it deliberately refuses IP, DHCP, routing, firewall and users. Third-party tools do most of the damage: 2GT MikroTik Manager, MikroDash, mikr and nasnet-panel already cover much of that space. The recommended path is to trial those tools first. If a real gap survives, build a narrow Svelte front end on a small backend, on the home server first, with the binary API as the main path and CMR as an optional adapter rather than a design foundation. No part of this research was tested on hardware, and no source measures a third-party web app on the be³ Media, so the next step is a short hardware spike, not backend code.

## Only two of the deployment options survive

| Option | Verdict | Deciding facts | Conditions |
|---|---|---|---|
| Separate home server | **Yes, best option** | No flash, RAM or container limits; history database fits easily; works with the ac² today | Needs an always-on box; holds router credentials; its path to the router crosses the network it changes |
| Container on hAP be³ Media | **Yes, conditionally; unproven** | arm64, 2 GB RAM, container package advertised; other projects already ship on-router containers | RouterOS 7.25.1 or later, USB SSD, one physical button press, `memory-max` set, hardware spike passed |
| Container on hAP ac² | **No** | 128 MB RAM, 16 MB flash, no Apps support, container starts reported to eat flash | Manage it remotely instead |
| Browser-only app served by the router | **No** | RouterOS lacks good CORS support, and credentials and polling need a backend | A proxy is required on any host |

The be³ Media fits on paper: a quad-core 64-bit IPQ-5322 at up to 1.5 GHz, **2 GB RAM and 512 MB NAND**, with container support and a one-click setup advertised ([MikroTik](https://mikrotik.com/product/hap_be3_media)). Packaging is well served too, because custom YAML apps exist from 7.22 and create the veth and NAT for you on arm64 or x86 ([Apps manual](https://manual.mikrotik.com/docs/containers/apps/)). MikroDash and nasnet-panel already run as RouterOS containers ([MikroDash](https://github.com/SecOps-7/MikroDash), [nasnet-panel](https://github.com/nasnet-community/nasnet-panel)), though neither is reported on this board.

The evidence for this board is thin. The research found no RAM, CPU or uptime figures for a custom web app on it, and no measurement of routing or Wi-Fi impact from running containers. MikroTik advises against internal storage and sets a disk target of **100 MB/s sequential and 10K random IOPS** ([Container manual](https://manual.mikrotik.com/docs/containers/), [Apps manual](https://manual.mikrotik.com/docs/containers/apps/)), which points to a USB SSD rather than a microSD card. Enabling containers needs a physical reset-button confirmation, so no remote install is possible ([Container manual](https://manual.mikrotik.com/docs/containers/)). Early firmware was rough: users reported dead Ethernet after updating to 7.24.2 ([forum](https://forum.mikrotik.com/t/hap-be-media-ethernet-ports-not-working-on-stable-routeros/273058)), and 7.25 fixed occasional packet loss on this board ([7.25 thread](https://forum.mikrotik.com/t/7-25-stable-is-released/273987)). Supply is also tight despite real owners: MikroTik's page still says "Coming soon!", and one UK retailer lists next arrivals on 11 December ([LinITX](https://linitx.com/product/mikrotik-hap-be3-media-wifi-7-router-access-point-ma53ug+hbeh/18454)).

One blocking unknown remains: no MikroTik page documents a container calling its own router's API, and no first-hand report of REST working that way was found. A 2023 user's container could not reach the router's SSH ([forum](https://forum.mikrotik.com/t/connect-to-router-via-ssh-from-container/169810)). The likely recipe is to target the veth gateway address with a narrow input-firewall rule. Version 7.25 added a `networkRouterIP` app variable, which suggests intent, but it is undocumented ([7.25 thread](https://forum.mikrotik.com/t/7-25-stable-is-released/273987)). This test should come first.

The hAP ac² fails for structural reasons. It has **128 MB RAM and 16 MB flash**, on 32-bit ARM ([MikroTik](https://mikrotik.com/product/hap_ac2)), and Apps exclude it. One user saw an Unbound container take free flash to zero on 7.19.3 even with its data on USB ([forum](https://forum.mikrotik.com/t/running-out-of-space-on-hap-ac2/172510?page=6)), and running out of storage forced a NetInstall in another case ([forum](https://forum.mikrotik.com/t/hapac2-out-of-hdd-space-safe-free-disk-space/173946)). The danger is not that a container fails to start. It is damaging a working router.

MikroTik's container warning also weighs against the on-router option: it offers "no security guarantee of any kind", and a compromise could leave a backdoor that survives removal ([Container manual](https://manual.mikrotik.com/docs/containers/)). A controller holding router credentials is exactly that high-value case, which is a further reason to start on the home server.

## The API can drive a controller, but no write is fully safe

RouterOS can feed a full controller, on one condition: the binary API over TLS on 8729 must be the main path. REST does not stream, stops at 60 seconds, and runs one user's requests one at a time ([REST manual](https://manual.mikrotik.com/docs/7.25/developer-guides/rest-api/)). The binary API has tagged concurrent commands and `listen` push ([API manual](https://help.mikrotik.com/docs/spaces/ROS/pages/47579160/API)). REST also had a session leak and an auth-header memory leak that were fixed only in 7.25, so 7.25 is the sensible floor for any REST polling ([7.25 changelog](https://upgrade.mikrotik.com/routeros/7.25/CHANGELOG)). The notes do not settle two matters. Container access to 8729 is unconfirmed, and polling cost on hAP-class hardware has never been published; the only figures come from a virtual lab router.

Writes are the real problem. RouterOS applies each command immediately, and has no native commit-confirm, per forum users ([forum](https://forum.mikrotik.com/t/commit-confirm-fashion-command-available/88542)). Version 7.18 added scriptable Safe Mode ([7.18 changelog](https://upgrade.mikrotik.com/routeros/7.18/CHANGELOG)), but evidence that it works over the binary API comes from one library's tests, not from MikroTik ([tik4net](https://github.com/danikf/tik4net/wiki/Connection-types-and-capabilities)). Its limits are serious. It covers **the 100 most recent actions**, and if it runs out of room it leaves Safe Mode with nothing undone. Rollback after a cut connection waits for a **9-minute TCP timeout**. It also applies router-wide, so other sessions' changes roll back too ([Configuration Management](https://manual.mikrotik.com/docs/7.25/getting-started/configuration-management/)). The usual fallback, a scheduled revert job, disappears in `home` device mode, and re-enabling the scheduler needs physical confirmation ([Device mode](https://manual.mikrotik.com/docs/system-information-and-utilities/device-mode/)). Which mode the be³ Media ships in was not established, so check it with `/system/device-mode/print`. Since container setup needs a button press anyway, that visit could also restore the scheduler (my inference).

MikroTik itself recommends a serial console for bridge VLAN filtering, because enabling it can lock you out and reset the bridge ([Bridge VLAN Table](https://help.mikrotik.com/docs/spaces/ROS/pages/28606465/Bridge+VLAN+Table)). A web UI cannot offer that promise, so the honest design treats VLAN filtering, the input firewall, `/ip/service` and management addressing as high-risk actions behind explicit warnings.

**On-router hosting has a safety blind spot that the research notes do not call out directly.** This is my inference, and it is untested. Safe Mode reacts only to session death, and the proposed check is a fresh connection from the controller. A controller in a container reaches the router over its own veth, so a change that cuts off the LAN may leave that session and that fresh connection working. The controller would then confirm a change that locked the user out. The confirmation therefore has to come from the user's browser: if the browser does not confirm within a set time, the backend rolls back. A home server does not have this blind spot, because its probe crosses the real network, though it pays the full 9-minute wait after a true lockout.

Credentials are the other structural limit. Policies are global rather than per menu, so a "firewall only" user is impossible, and the built-in `read` group includes `sensitive` and `reboot` ([User manual](https://help.mikrotik.com/docs/spaces/ROS/pages/8978504/User)). The writer credential should be treated as equal to admin.

## Four UniFi features stop at RouterOS limits

Most of UniFi's surface maps onto RouterOS: client lists, Wi-Fi management, VLANs, guest portals, roaming and notifications are all possible with caveats. Four features are where the resemblance stops, and any mockup screen showing them promises something the platform cannot deliver.

Per-client application statistics are the largest gap. The new `/tool/apptraffic` is beta, and its stats are keyed by application and category, with no client, IP or MAC field ([apptraffic stats](https://manual.mikrotik.com/docs/cli-reference/tool/apptraffic/stats/)). App-based blocking is the second gap: no application-aware matcher was found, and the Layer-7 matcher handles only unencrypted HTTP ([Layer7](https://manual.mikrotik.com/docs/firewall-and-quality-of-service/firewall/layer7/)). UniFi-style device fingerprinting is the third, because option 55 is reported unavailable to lease scripts and random MACs defeat vendor lookup ([forum](https://forum.mikrotik.com/t/dhcp-server-lease-script-is-client-sent-option-55-parameter-request-list-accessible/269752)). Non-disruptive RF scanning is the fourth, because `frequency-scan` disconnects clients ([Wi-Fi manual](https://manual.mikrotik.com/docs/wireless/wifi/)).

The monitoring needed to fake these features can hurt the router. A running sniffer, torch, mac-scan or ip-scan conflicts with FastTrack ([MikroTik help](https://help.mikrotik.com/docs/spaces/ROS/pages/130220087/Firewall+and+QoS+Case+Studies)), and FastTrack packets bypass simple queues and connection tracking ([Packet Flow](https://manual.mikrotik.com/docs/firewall-and-quality-of-service/packet-flow-in-routeros/)). Client counters therefore come from several partial sources, and long-term history has to be stored by tikontrol. Whether apptraffic even classifies FastTracked traffic is unknown, and its CPU cost is unpublished.

Zone firewall works only as a UI abstraction over interface lists, and only if tikontrol owns the rule set. That points to the deepest design problem: representing an arbitrary hand-built RouterOS config safely. MikroTik avoids it by owning only its own objects ([CMR manual](https://manual.mikrotik.com/docs/management-tools/cmr/)), while 2GT attacks it with lockout prediction ([2GT](https://github.com/2GT-Media-Group-LLC/mikrotik-manager)). Tikontrol must pick one of those approaches or restrict the topologies it supports.

## CMR breaks PLAN's foundation, and competitors break its rationale

CMR is real but premature as a dependency. It arrived in 7.26beta1 in early October 2026 as an "initial implementation" ([7.26beta thread](https://forum.mikrotik.com/t/7-26beta-development-is-released/273582)). The current channels are stable 7.25.1 and development 7.26beta5, so **CMR is in no stable release** ([stable](https://upgrade.mikrotik.com/routeros/NEWESTa7.stable), [development](https://upgrade.mikrotik.com/routeros/NEWESTa7.development)). Staff say 7.26 is coming "soon", but no date exists. It already delivers inventory, fleet upgrades, alerts, topology, app stats, Wi-Fi and VLAN provisioning. It excludes IP, DHCP, routing, firewall and users ([CMR manual](https://manual.mikrotik.com/docs/management-tools/cmr/)). No price was found, and the package ships in the normal download, but the manual never says it is free.

Three facts undercut CMR as the design centre. First, it takes over rather than adopts: it "does not adopt existing configuration", works best on default configs, replaces selected radios, and moves ports into `cmr-bridge`, which can cut management access ([CMR manual](https://manual.mikrotik.com/docs/management-tools/cmr/)). One reviewer lost about three hours to a VLAN rule that needed local console recovery ([Link Technologies](https://shop.linktechs.net/cmr_first_look)). Second, staff say all of CMR is available over REST, yet no REST reference exists. Users report that `/cmr/device/dashboard` never returns and stalls other calls ([forum](https://forum.mikrotik.com/t/claude-and-codex-try-out-cmr-in-7-26beta-mostly-successful/273613)), and live Wi-Fi client counts are not available from the controller API yet ([ha-cmr](https://github.com/Anrijs/ha-cmr)). Third, the ac² is not a realistic server: an arm package exists, but staff want "powerful ARM64 routers with enough space" ([forum](https://forum.mikrotik.com/t/7-26beta-development-is-released/273582?page=2)), although RB4011 approval shows that is loose guidance. No RAM or device limits are published. Safe writes also clash with CMR's REST route, because Safe Mode is unavailable over REST. Whether `/cmr` menus behave over the binary API is untested.

| Project | Traction (2026-11-04) | Relevance | Caveat |
|---|---|---|---|
| [2GT MikroTik Manager](https://github.com/2GT-Media-Group-LLC/mikrotik-manager) | 248 stars, 8 contributors, v1.0.5, AGPL-3.0 | VLANs, SSIDs, firewall, firmware, auto-revert, lockout prediction | On-router use unconfirmed; 57 open issues |
| [MikroDash](https://github.com/SecOps-7/MikroDash) | 639 stars, MIT | On-router container, multi-router, config pages | Depth unchecked |
| [mikr](https://mikr.app/) | 123 stars, v2.2.0, one contributor | arm64 container; free up to 10 devices, then paid; vendor claims about 130 MB RAM for 25 devices | Commercial, no SPDX licence on GitHub |
| [nasnet-panel](https://github.com/nasnet-community/nasnet-panel) | 27 stars, pre-1.0, MIT | On-router, firewall, DHCP, VPN, batch commands with rollback | Sentry on by default in production builds; multi-device scope unchecked |

None of these was run for this research, and stars do not measure reliability. Even so, the picture is clear: on-router hosting is no longer a differentiator, and neither is a feature list. MikroTik's normis has said an LLM can build a small container app with a nice GUI on CMR ([forum](https://forum.mikrotik.com/t/claude-and-codex-try-out-cmr-in-7-26beta-mostly-successful/273613)). Dashboards are now cheap, and what stays scarce is trust, write safety and years of maintenance across RouterOS releases.

The case for building is not empty. Nothing found clearly delivers a UniFi-grade guided experience, on one box, that joins CMR's zero-touch clients to the gateway functions CMR refuses. Most rivals are young and single-maintainer, and MikroTik's UI history suggests polish may stay open, though that is judgement. The audience is narrower than forum demand implies, because people who want UniFi simplicity often buy UniFi, while MikroTik enthusiasts often prefer raw control.

The verdict is to **not build a full independent controller**. Prefer, in order: use CMR with an existing tool; contribute to MikroDash or nasnet-panel; or build a thin opinionated UI. As a personal learning project, tikontrol needs no market justification, but that is a different goal and should be scoped as one.

PLAN should change in four ways. CMR becomes an optional, version-gated adapter, with per-device API access as the core. The go-mikrotik-cmr reverse-engineered route stays out, because it is one author's work and lacks password pairing ([go-mikrotik-cmr](https://github.com/AthenaNetworks/go-mikrotik-cmr)), and MikroTik's licence terms on reverse engineering were not read. Hosting flips to home server first, using the same image for the be³ Media later. Rust remains acceptable, but it is not decisive. Its small footprint buys little on 2 GB and does not rescue the ac². No Rust RouterOS client was evaluated in this research, and the Safe Mode evidence lives in a different library, so that logic would need its own testing.

## The biggest risks are maintenance, lockouts and credentials

| Rank | Risk | Why it matters | Response |
|---|---|---|---|
| 1 | Redundancy | Active projects already cover the idea, and MikroTik can extend CMR | Trial existing tools before writing backend code |
| 2 | Lockouts from writes | No transactions; undocumented Safe Mode path; 9-minute worst case | Read-only first; browser-confirmed changes; no VLAN filtering toggle in v1 |
| 3 | API drift | [Breaking changes in almost every 7.x](https://upgrade.mikrotik.com/routeros/7.24/CHANGELOG), no API version or stability policy found | Feature-detect with `/console/inspect`, run CHR contract tests per release, watch [schema diffs](https://tikoci.github.io/restraml/diff.html) |
| 4 | Credential compromise | Writer equals admin; backups and stored exports can leak secrets; on-router container carries no security guarantee | Own the image, avoid Layer 2 and privileged mode, split reader and writer users, encrypt stored secrets |
| 5 | CMR beta churn | Paths, behaviour and release timing can all shift | Keep it optional until after 7.26 stable |
| 6 | be³ unknowns | Young board, no container benchmarks, USB and heat concerns | Pass the hardware spike; verify the disk is mounted before relying on start-on-boot |
| 7 | Solo-maintainer burnout | The inferred failure pattern is a one-author burst then silence; no post-mortems exist | Keep scope small enough to survive a year of neglect |
| 8 | Trademark and design | EU law bars presenting goods as "imitations or replicas" ([Directive 2006/114](https://www.legislation.gov.uk/eudr/2006/114/article/4)); EU design law now covers GUIs ([HSF Kramer](https://www.hsfkramer.com/notes/ip/2025-05/eu-design-reform-begins-key-provisions-of-eu-regulation-2024-2822-effective-from-1-may)) | See below |

The legal risk is manageable, and it is mostly a marketing choice. This is not legal advice, and no primary judgment could be opened. Copying functions and workflows looks low risk, since *SAS v World Programming* keeps functionality outside copyright ([Fieldfisher](https://www.fieldfisher.com/en/insights/sas-institute-inc-v-world-programming-limited)), but a GUI's specific expression can be protected ([Fieldfisher](https://www.fieldfisher.com/en/insights/graphical-user-interfaces-can-be-protected-by-copyright-rules-european-court)). Keep "UniFi" out of the name, logo and tagline, drop the phrase "UniFi-inspired" from public copy, and use your own icons, colours and layout. No Ubiquiti action against a look-alike UI was found, but the search was limited, and Ubiquiti's design registrations were not checked. MikroTik's brand page requires a licence for logos and bars implied endorsement ([MikroTik](https://mikrotik.com/logo)). Plain-text "works with RouterOS" with a non-affiliation note is the safer form. The "Tik" fragment in the name is covered by no published rule, so a short email to MikroTik's brand team would settle it cheaply.

## Conclusion

The research shifts the question from "can this run on a router?" to "who keeps it safe through every RouterOS release?". Hosting is the easy part. The defensible asset is no longer a dashboard but a write path users can trust, and on-router hosting makes that harder rather than easier. CMR's arrival helps here, oddly enough: it settles what not to build and leaves a sharper target.

Three cheap gates should come before any backend. Spend a week running MikroDash and 2GT against a lab or spare device, and write down what is still missing. Then run one hardware session on a be³ Media or CHR that answers the open questions: container access to 8729 and REST, dotted `.proplist` names, `/safe-mode` behaviour, device mode, and polling cost. Finally, trim the Svelte mockup to what RouterOS can actually report. If the gap list from the first gate is short, contributing upstream is the better use of the mockup's UX ideas. If it is long and specific, tikontrol has its reason to exist, and that list is its scope.
